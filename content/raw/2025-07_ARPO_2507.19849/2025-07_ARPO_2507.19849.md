# Agentic Reinforced Policy Optimization

## 一句话结论

ARPO 的新增点不是 agent runtime 接入，也不是分布式训练系统，而是把多轮工具调用 RL 里的两个细节单独拎出来做算法：**工具返回后哪些位置更值得追加采样**，以及**从某个工具反馈节点分叉出来的多条轨迹，shared prefix 和 branch suffix 应该怎样吃 advantage**。

相对 Agent Lightning 和 AgentRL，它更像一个可插入的 rollout / advantage 模块：

- Agent Lightning 解决“现有 agent 怎么拆成 transition 并接进 RL trainer”。
- AgentRL 解决“多任务多轮环境怎么异步跑得快、混训更稳”。
- ARPO 解决“在工具返回后的高不确定步骤上怎么少花预算、多探索，并让分叉轨迹的 credit 不全都糊成整条 trajectory reward”。

我的判断：**adaptive rollout 值得单独记，stepwise credit assignment 也值得记，但要带限定词。**前者是清楚的工程/算法 idea：用工具返回后的 token entropy 触发 partial rollout 分支；后者在论文中更像“partial rollout 后如何合理使用 GRPO advantage”的实现细节和理论解释，不是完全解决长程 credit assignment 的通用方案。

## 这篇放在阅读路线里的位置

前面三篇已经形成一条线：

| 论文 | 主要回答 |
| --- | --- |
| Agent-Diff / tau-bench | 怎么构造可验证 agent 环境和最终 reward/verifier。 |
| Agent Lightning | 已有 agent runtime 怎么拆成 LLM-call transition 并接入 RL。 |
| AgentRL | 多轮多任务 rollout、环境 worker 和 trainer 怎么异步扩展。 |
| ARPO | 在一条多轮工具调用轨迹内部，哪些工具反馈节点值得多采样，分叉轨迹的 advantage 怎么分配。 |

所以 ARPO 的位置比 AgentRL 更“算法局部”。它不提供通用 agent harness，也不处理环境生命周期、任务调度、policy lag 或多任务 normalization；它默认已经有 tool-use agent、reward 和 RL 框架，然后改 rollout 采样策略和 advantage 使用方式。

## 解决什么问题

传统 GRPO/DAPO/REINFORCE++ 用在 tool-use agent 上时，常见做法是同一个问题采样多条完整工具调用轨迹，最后按最终答案 reward 做 group relative advantage。问题是：

1. 工具调用后的 observation 会把模型带到新的局部状态，尤其是搜索结果、网页内容、Python 输出等外部反馈。
2. 模型在这些反馈后的前几十个 token 往往更不确定，token entropy 明显升高。
3. 整条 trajectory-level sampling 会把预算平均花在完整轨迹上，未必重点探索这些“工具反馈后真正分叉”的关键步骤。
4. 如果从某个工具反馈节点复制出多条后续路径，shared prefix 与 branch suffix 的 credit 不能简单当作完全独立轨迹处理。

ARPO 的假设是：**工具返回后的高 entropy token 是 agent 决策的不稳定点，也是值得追加探索的局部节点。**

论文的 pilot experiment 观察到三点：

- 每次 tool call feedback 后的前 10-50 个 token entropy 会明显上升。
- 早期 reasoning 也会有 entropy 上升，但通常低于工具反馈后的 entropy。
- search feedback 比 Python feedback 引入更大的 entropy 波动，因为搜索返回的是丰富文本，Python 输出多是确定性数字。

这就是 adaptive rollout 的动机。

## 方法 / 系统怎么做

### 1. Agentic RL 基础形式

论文把 agentic rollout 写成两部分：

```text
P_theta(R, y | x; T)
  = product_t P_theta(R_t | R_<t, x; T)
    * product_t P_theta(y_t | y_<t, R, x; T)
```

其中：

- `x` 是题目或任务输入。
- `T` 是可用工具集合。
- `R` 是 interleaved tool-use reasoning trajectory。
- `y` 是最终答案。
- reward `r_phi(x, y)` 通常来自可验证答案或 LLM-as-judge / F1。

ARPO 仍然建在 GRPO / REINFORCE++ 这类 rule-based RL 算法上，不是从零发明一个新的 RL objective。它改的是 rollout 过程和 advantage attribution。

### 2. Entropy-based Adaptive Rollout

ARPO 给定总 rollout budget `M`，先只用 `N` 条做全局 trajectory-level sampling，剩下的 `M - N` 留作 partial sampling budget。

流程是：

1. **初始化全局采样**：对输入问题 `q` 生成 `N` 条初始轨迹，计算每条轨迹开头 `k` 个 token 的 entropy，作为 `H_initial`。
2. **监控工具返回后的 entropy**：每次工具调用后，把工具结果拼回上下文，让模型继续生成 `k` 个 token，计算当前步骤 entropy `H_t`。
3. **计算 entropy change**：

```text
Delta H_t = Normalize(H_t - H_initial)
```

4. **决定是否分叉**：

```text
P_t = alpha + beta * Delta H_t

if P_t > tau:
  Branch(Z)
else:
  Continue
```

如果 entropy 增量足够高，就从当前节点 fork 出 `Z` 条 partial reasoning paths；否则继续原轨迹。

5. **预算终止**：当分叉数量达到 `M - N`，停止继续分叉；如果所有路径提前结束但还没用完预算，则补充普通全局采样。

这和 beam search 的相似点是“从中间节点扩展分支”；不同点是分支触发不是固定 beam width，而是工具返回后的 entropy change。

### 3. Advantage Attribution Estimation

Adaptive rollout 会产生一种结构：多条轨迹共享前缀，在某个工具反馈后的节点分叉，之后每条路径有不同后缀和最终 reward。

ARPO 讨论两种 advantage 处理：

#### Hard advantage

对 branch suffix，用各自完整轨迹 reward 计算 normalized group advantage：

```text
A_i = (R_i - mean(R_1 ... R_G)) / std(R_1 ... R_G)
```

对 shared prefix，把共享该前缀的 `d` 条轨迹 advantage 平均：

```text
A_shared = average(A_1 ... A_d)
```

直觉：共享前缀不应因为某一条 branch 成功或失败而独占 credit；branch 后缀才承接各自差异。

#### Soft advantage

实际默认用 soft setting，也就是保留 GRPO objective。论文认为 partial rollout 形成的 shared token 和 individual token 会通过 importance sampling ratio 的上下文前缀自动体现差异：

- 如果两条轨迹在 token `t` 前的 prefix 相同，`r_i,t(theta)` 相同，shared tokens 的更新近似吃 group average advantage。
- 如果 prefix 已经分叉，`r_i,t(theta)` 不同，branch tokens 吃各自轨迹的 advantage。

作者给了 appendix proof，并在 Figure 5 中显示 soft setting 比 hard setting reward 更稳定，所以 ARPO 默认 soft advantage estimation。

这里要谨慎：它不是学了一个显式 value function，也不是为每个工具调用估计真实因果贡献；它主要利用 partial rollout 的共享/分叉结构，让 GRPO 的 token-level loss 在 shared prefix 与 branch suffix 上表现得更合理。

### 4. Hierarchical reward

论文沿用 Tool-Star 风格 reward：

- correctness / accuracy reward。
- format reward。
- multi-tool collaboration reward `r_M`：当答案正确、工具格式正确，并且同时使用 `<search>` 和 `<python>` 时给额外奖励。

大意是：

```text
if format good and accuracy > 0:
  R = max(accuracy + r_M, accuracy)
elif format good and accuracy == 0:
  R = 0
else:
  R = -1
```

这说明 ARPO 的效果仍然依赖可用 reward 和工具格式约束；它没有解决 verifier 质量问题。

## 实验设计和结果怎么读

### 任务与训练设置

论文覆盖三类共 13 个 benchmark：

- 数学推理：AIME2024、AIME2025、MATH500、MATH、GSM8K。
- 知识密集推理：WebWalker、HotpotQA、2WikiMultihopQA、MuSiQue、Bamboogle。
- Deep Search：GAIA、WebWalkerQA、HLE、xbench-DeepSearch。

训练路线是 cold-start SFT + RL：

- SFT 用 LLaMAFactory，Tool-Star 54K 样本，加 STILL 0.8K 数学数据。
- RL 对数学/知识推理用 Tool-Star 10K RL 样本。
- RL 对 deep search 只用 1K mixed hard search samples。
- Deep reasoning 的 7B 设置：batch 128、PPO mini-batch 16、global rollout size 16、initial sampling size 8、response cap 4096 tokens、8 H800、2 epochs。
- Deep search 的 8B/14B response cap 扩到 8192 tokens；14B 用 16 H800；1K 数据训练 5 epochs。

### Table 1：数学和知识推理

ARPO 在 Qwen2.5-3B、Llama3.1-8B、Qwen2.5-7B 三个 backbone 上平均都强于 GRPO/DAPO/REINFORCE++：

| Backbone | Direct | GRPO | DAPO | ARPO |
| --- | ---: | ---: | ---: | ---: |
| Qwen2.5-3B | 26.1 | 50.4 | 50.6 | 52.8 |
| Llama3.1-8B | 28.8 | 51.1 | 50.4 | 55.3 |
| Qwen2.5-7B | 32.0 | 56.5 | 54.8 | 58.3 |

正确解读：收益存在，但在这 10 个任务上多是几个百分点，不是数量级提升。更值得看的不是平均分，而是它在 WebWalker、HotpotQA、2Wiki、Bamboogle 等需要工具反馈整合的任务上更有优势。

### Table 2：Deep search

Deep search 是 ARPO 更适合展示的场景，因为它有频繁搜索、网页阅读和多步工具反馈。

Qwen3-8B：

- GRPO: GAIA avg 32.0、WebWalkerQA avg 29.0、HLE avg 7.8、XBench avg 20.0。
- ARPO: GAIA avg 38.8、WebWalkerQA avg 30.5、HLE avg 8.8、XBench avg 25.0。

Qwen3-14B：

- GRPO: GAIA avg 36.9、WebWalkerQA avg 30.0、HLE avg 8.6、XBench avg 27.0。
- ARPO: GAIA avg 43.7、WebWalkerQA avg 36.0、HLE avg 10.0、XBench avg 32.0。

这支持“工具反馈后的局部探索有价值”，尤其在 GAIA/WebWalkerQA/XBench 这种要多次搜索整合的任务中。

### Figure 7：工具调用效率

论文声称 ARPO 比 GRPO 使用约一半 tool calls，却有更高 overall accuracy。这个证据来自 Qwen2.5-7B 的 tool-call efficiency analysis。

这点值得记，但不能扩大解释：

- 它是训练阶段 tool-call budget 的比较，不是所有部署场景都自动省一半推理工具调用。
- 省预算来自 selective branch：只在高 entropy 工具反馈点扩展，而不是每条完整轨迹都重新跑到底。
- 仍然需要计算 token entropy 和维护 partial rollout tree；只是相对完整轨迹重采样，工具环境调用更少。

### Figure 8：超参 scaling

三个结论比较实用：

- entropy weight / entropy value 不是越大越好，0.4 左右最好；过度依赖 entropy 会伤害采样多样性。
- `M=16` 时，`N=8` 最好，也就是全局采样与局部采样预算约 1:1。
- global rollout size 增大总体提升性能，说明它仍然吃 rollout budget scaling。

因此 adaptive rollout 不是“只看 entropy 就够了”；它需要在 base sampling probability、entropy trigger 和全局轨迹覆盖之间平衡。

## STAR 分析

| 项 | 内容 |
| --- | --- |
| Situation | 多轮 tool-use agent 的关键决策常发生在工具返回之后，传统 trajectory-level RL 用完整轨迹采样和最终 reward，容易忽略这些局部高不确定步骤。 |
| Task | 在固定 rollout/tool-call 预算下，更有效地探索工具反馈后的分叉行为，并让共享前缀与分叉后缀得到更合理的 advantage 信号。 |
| Action | 先采样 `N` 条全局轨迹，保留 `M-N` 预算；监控工具返回后前 `k` 个 token 的 entropy change；当 `alpha + beta * Delta H_t > tau` 时从当前节点 fork partial rollouts；用 hard/soft advantage attribution 处理 shared prefix 和 branch suffix。 |
| Result | 在 10 个数学/知识任务和 deep search benchmark 上普遍超过 GRPO/DAPO/REINFORCE++；deep search 中 Qwen3-8B/14B 相比 GRPO 有更明显提升；Qwen2.5-7B 的工具调用效率分析显示约半数工具调用预算下表现更高。 |

## 和 Agent Lightning 的区别

| 问题 | Agent Lightning | ARPO |
| --- | --- | --- |
| 首要目标 | 任意现有 agent runtime 接入 RL trainer。 | 多轮工具调用轨迹内部的局部采样和 advantage attribution。 |
| 核心单位 | 每次 LLM call 的 transition。 | 工具返回后的 token entropy segment / partial rollout branch。 |
| 主要贡献 | Unified data interface、Training-Agent Disaggregation、trace instrumentation。 | Entropy-triggered partial rollout、shared/individual advantage 处理。 |
| Credit assignment | 当前实现比较粗，可替换；强调接口。 | 专门处理 partial rollout 造成的 shared prefix 和 branch suffix。 |
| 工程范围 | agent runtime、trainer、observability、OpenAI-like endpoint。 | 主要是 RL rollout 算法，不是 agent 系统架构。 |

可以组合的方式：Agent Lightning 负责把真实 agent trace 拆成 transition 并接入 trainer；ARPO 负责在每个可工具交互的 transition/trajectory 内决定哪里追加 partial rollout。

但两者粒度不完全相同：Agent Lightning 把一次 LLM call 当 action；ARPO 更关心一次连续生成中工具返回后 token-level / segment-level 分叉。

## 和 AgentRL 的区别

| 问题 | AgentRL | ARPO |
| --- | --- | --- |
| 首要目标 | 多任务多轮 RL 的异步吞吐、环境部署和混训稳定性。 | 单任务/多任务中工具反馈节点的高效探索。 |
| 系统重点 | rollout engine、training engine、container worker、central controller。 | rollout 内的 entropy monitoring、partial branch、advantage attribution。 |
| 探索机制 | cross-policy sampling，用当前/旧 policy 版本在 step-level 混合探索。 | 同一 policy 从高 entropy 工具反馈节点 fork partial paths。 |
| 稳定机制 | task-wise advantage normalization。 | shared prefix / individual suffix 的 hard/soft advantage estimation。 |
| 成本问题 | 异步减少等待，提高 GPU/token throughput。 | selective branch 减少不必要的完整工具轨迹重采样。 |

两者可以互补：AgentRL 的异步 worker/controller 可以承载 ARPO rollout；ARPO 的 entropy trigger 可以替换 AgentRL 中普通 GRPO 的全轨迹采样策略。但论文没有真正实现这种组合，也没有讨论异步环境下 partial rollout tree 的调度成本。

## Adaptive rollout 值不值得单独记

值得，原因有三点：

1. **它抓住了工具 agent 和单轮 reasoning RL 的本质差异。**工具反馈会把模型带到外部分布，工具返回后的前几十个 token 是重新规划、验证、选择下一步动作的位置。
2. **它是可实现的预算分配策略。**不是泛泛说“多探索”，而是把固定 rollout budget 拆成全局 `N` 和局部 `M-N`，用 entropy change 决定在哪里 fork。
3. **它直接对应成本问题。**完整轨迹重采样会重复执行大量工具调用；partial rollout 可以复用共享前缀和已有工具反馈，只在关键节点扩展。

需要同时记住的限制：

- entropy 是 proxy，不等于真实价值或因果重要性。
- 搜索结果这种 rich textual feedback 更容易触发 entropy；Python 数值输出的收益可能小。
- 需要能从中间状态恢复/复制 rollout；真实浏览器、数据库、机器人环境里这可能很难。
- 如果工具调用有副作用，partial branch 不能简单复用环境状态，必须有 snapshot / rollback / sandbox。

## Stepwise credit assignment 值不值得单独记

也值得，但要写成“partial rollout advantage attribution”，不要写成“解决了 credit assignment”。

值得记的点：

- 它明确区分 shared prefix 和 branch suffix。
- shared prefix 的 credit 应该来自多个后续 branch 的平均效果，而不是某一条分支的最终 reward。
- branch suffix 才应该更强地吃各自最终 reward 的差异。
- soft setting 说明即便保留 GRPO objective，只要 rollout 结构中有共享/分叉，importance ratio 和 prefix context 也会让 shared / individual token 的更新表现不同。

不能误读的点：

- 没有 learned value function。
- 没有对每个工具调用做真实 counterfactual causal attribution。
- 没有 dense environment reward。
- 对长程多工具链中“第一个错误步骤”在哪里，仍然没有可靠诊断。
- 它只在 partial rollout tree 结构下比较自然；普通完整轨迹采样并不会自动得到这种好处。

我的记忆方式：

```text
adaptive rollout = where to branch
advantage attribution = how shared prefix and branch suffix learn after branching
```

## 和我的研究方向的关系

### Agent harness

高相关。ARPO 提醒我们，agent harness 不能只保存最终 transcript，还要保存：

- 每次 tool call 前后的 model context。
- 工具返回后的前若干 token entropy / uncertainty signal。
- 是否从某个环境状态 fork 过 partial rollout。
- 分叉路径共享了哪些前缀，在哪个工具反馈节点分开。
- 每条分支的最终 reward / verifier 结果。

如果以后要做低成本 agent RL，这些日志字段比普通聊天记录更有训练价值。

### Interaction model

中等相关。ARPO 没有做人机交互，但“工具反馈后高不确定”可以类比到交互系统：

- 用户纠正、打断、确认、环境状态变化之后，模型也可能进入高不确定状态。
- 这些节点可能最值得做 clarification、ask-for-confirmation、或者 human-in-the-loop branch。
- 对用户可见 execution feedback 来说，高 entropy 节点可能是需要解释“我正在重新判断”的地方。

但论文没有用户研究、控制权设计或透明度机制。

### 机器人 / embodied agent

概念相关，直接证据不足。机器人环境中每次感知反馈、动作执行结果、失败恢复都可能是高不确定节点；adaptive rollout 的思想可以迁移到 simulator 中的 branch / replay。

但真实机器人有额外难点：

- 环境状态不可随意复制，partial rollout 需要 simulator 或 state checkpoint。
- 连续控制不是文本 token，entropy 需要重新定义为 action distribution uncertainty、world model uncertainty 或 value uncertainty。
- 工具调用副作用在机器人里是真实物理变化，不能像文本搜索那样廉价重放。
- 安全约束比最终答案 reward 更重要。

### Memory / experience replay

ARPO 本身没有长期记忆，但 partial rollout tree 是很好的 experience representation：

```text
same prefix -> tool feedback -> branch A success / branch B fail
```

这比单条成功/失败轨迹更适合做反思、错误归因、case retrieval 和训练数据筛选。

## 局限和不要误读

1. **不是 agent runtime 框架。**没有解决 trace 接入、环境 worker、异步训练、任务调度或部署问题。
2. **不是通用 credit assignment 终局答案。**它处理的是 partial rollout tree 下 shared/branch token 的 advantage，不是全链路因果归因。
3. **entropy 只是启发式。**高 entropy 可能是有价值探索点，也可能是模型困惑、工具结果噪声或格式混乱。
4. **训练 reward 仍然脆弱。**数学/QA 用 F1、deep search 用 LLM-as-judge，reward hacking 和 verifier 偏差仍可能存在。
5. **deep search 依赖 browser agent 能力。**Table 3 显示 browser agent 越强结果越好，这意味着收益不全来自 ARPO 算法本身。
6. **半工具预算不要泛化。**这是特定 Qwen2.5-7B 训练分析，不代表所有任务、所有环境、推理阶段都省一半。
7. **工具有副作用时实现复杂。**partial branch 需要可复制环境状态；真实 API、数据库、机器人动作需要 sandbox、snapshot 或补偿机制。
8. **理论部分更多是合理化。**GPG theorem 说明 macro-action segmentation 可以纳入 policy gradient，但不自动证明 entropy trigger 是最优分叉准则。
9. **没有多模态、实时交互或机器人实验。**

## 可复用点

1. 训练日志里记录工具返回后的 token entropy，尤其是前 10-50 token。
2. 把 rollout budget 分成 global trajectory budget 和 partial branch budget。
3. 对搜索、网页、数据库这类可 snapshot 的工具环境，优先在高 entropy 节点做 partial rollout。
4. 分叉轨迹要显式记录共享前缀和分叉点。
5. shared prefix 的 credit 不要简单绑定某一条分支最终 reward；至少做 branch average。
6. 评估工具调用效率时同时看 accuracy 和 total tool calls，而不是只看最终分数。
7. 对深度搜索 agent，区分 retriever/snippet、browser agent、reasoning model 三个贡献来源。

## 下一步问题

- CacheRL 是否从另一条路线降低 rollout 成本：缓存已有 rollout / tool results，而不是只在高 entropy 点分叉？
- ARPO 的 entropy trigger 能不能和 AgentRL 的 stale policy cross sampling 合并：高 entropy 节点既 fork partial paths，也随机用旧 policy 生成分支？
- 在 Agent-Diff / tau-bench 这种 state-diff verifier 下，ARPO 的收益是否仍然成立？
- 如果 reward 是 sparse binary success，而不是 F1/LLM judge，soft advantage 是否还稳定？
- 对有副作用工具，如何做 environment snapshot、rollback 和 branch isolation？
- 对 robot/VLA，entropy 应该来自 action distribution、language planner token、world model uncertainty，还是 verifier disagreement？

## 记忆钩子

**ARPO = 工具返回后看 entropy，entropy 高就从该节点 fork partial rollout；shared prefix 吃平均 credit，branch suffix 吃各自 credit。**

它相对 Agent Lightning / AgentRL 的价值在“轨迹内部的局部探索和 advantage attribution”，不是 agent 接入框架，也不是训练集群系统。
