# MUA-RL

## 一句话结论

MUA-RL 的核心贡献是把 **LLM-simulated user** 放进 agentic tool-use 的 RL rollout 里。它训练的不是“给定一个固定 prompt 怎么调用工具”，而是“用户会追问、补充、改变要求时，agent 如何一边沟通澄清，一边调用工具完成任务”。

这篇对用户交互型 agent 很重要：它把 user-agent-tool/database 三方动态交互纳入训练，而不是只优化单轮答案或固定脚本下的 tool call。

![MUA-RL main results](raw/2025-08_MUA_RL_2508.18669/assets/fig1_main_results.png)

## 这篇放在阅读路线里的位置

前面几篇更多从系统和训练接口角度推进：

| 论文 | 关注点 |
|---|---|
| Agent Lightning | 已有 agent trace 怎么变成 transition。 |
| AgentRL / AgentJet | 多环境、多任务、多模型 rollout-training 怎么跑起来。 |
| ARPO / ContextRL | 多轮轨迹里哪里该探索、怎么学 context grounding。 |
| MUA-RL | 用户本身是动态参与者时，怎么把用户模拟放进 RL loop。 |

MUA-RL 的位置很明确：它不是最底层的训练系统，也不是 benchmark paper，而是一个 **multi-turn user-interacting RL recipe**。如果我们之后做客服、陪伴、机器人协作、可打断 agent，这篇比纯 tool-use 论文更接近真实交互。

## 解决什么问题

传统 tool-use RL 往往是：给模型一个固定任务，模型自己调用工具，最后根据结果给 reward。这缺了一个真实世界里很关键的东西：**用户会动态变化**。

真实多轮交互里，用户可能：

- 一开始说不清楚需求，需要 agent 追问。
- 根据 agent 的回答改变目标或补充限制。
- 要求确认某些细节，例如价格是否不变、是否真的提交修改。
- 在 agent 已经查到信息后提出新要求。
- 和 agent 一起推动任务，而不是只在开头给一个静态 prompt。

MUA-RL 认为，agent 要学会两件事：

1. **和用户沟通**：澄清、确认、解释、遵守 policy。
2. **和数据库/工具交互**：查询、修改、验证状态。

如果 RL rollout 里没有用户角色，模型学到的只是静态工具调用，不一定能应对真实用户互动。

## 任务形式化

论文把多轮 tool-use 任务写成一个三元组：

```text
(T, M, O)
```

含义是：

- `T`：tool set space，工具空间。
- `M`：message space，agent 发给用户的自然语言消息空间。
- `O = O_db union O_user`：观察空间，包括数据库观察 `O_db` 和用户观察 `O_user`。

一条多轮轨迹可以写成：

```text
(o_1,user -> t_1 -> o_1,db -> ... -> m_1),
...,
(o_k,user -> t_j -> o_j,db -> ... -> t_{j+j_k} -> o_{j+j_k},db -> m_k),
...
```

直观解释：

- 用户先发一条消息 `o_user`。
- agent 可以调用一个或多个工具 `t_i`。
- 每次工具调用会返回数据库观察 `o_db`。
- agent 最后给用户一条消息 `m_k`。
- 下一轮用户可能继续回应，形成新的 `o_user`。

![Multi-turn tool-use trajectory](raw/2025-08_MUA_RL_2508.18669/assets/fig2_multiturn_trajectory.png)

这和普通 tool-use 最大的区别是：一轮里可能有多个 tool call，轮与轮之间还有用户反馈。agent 必须自己决定什么时候查工具、什么时候问用户、什么时候执行更新操作。

## Cold-start 数据：先让模型会基本工具调用

MUA-RL 不是直接从 base model 做 RL。它先做轻量 SFT cold-start，因为多轮工具任务太难，模型需要先学会基本格式和工具语义。

论文构造了两条数据合成 pipeline：

![Data synthesis pipeline](raw/2025-08_MUA_RL_2508.18669/assets/fig3_data_synthesis_pipeline.png)

### 1. LLM 模拟工具返回

流程是：

1. 人和 LLM 设计领域、database schema、tool descriptions、domain policy。
2. LLM 生成小型 synthetic database，作为工具模拟器的 memory。
3. 三个 LLM 协作生成轨迹：agent LLM、user LLM、tool LLM。
4. 当 agent 调工具时，把 tool name 和 arguments 发给 tool LLM，由它基于 memory 生成 tool response。

优点是灵活，缺点是 tool LLM 可能幻觉或不严格。

### 2. 真实 MCP server 执行工具

MCP 版本更接近真实环境：

1. 工具由 MCP server 提供。
2. agent LLM 和 user LLM 交互。
3. 真正的 tool execution 由 MCP server 完成。

这样减少了手工设计工具和模拟工具响应的成本，也更接近真实系统。

所有 cold-start 轨迹还会做双重验证：人工专家标注 + DeepSeek-R1 评估，用来过滤无效轨迹。

## MUA-RL rollout：三种 rollout 的区别

![Three rollout processes](raw/2025-08_MUA_RL_2508.18669/assets/fig4_rollout_processes.png)

论文区分三类 rollout：

| 类型 | 过程 | 局限 |
|---|---|---|
| Text-based rollout | 模型只生成文本，最后拿 reward。 | 不训练真实工具使用。 |
| Multi-step rollout with tool execution | 模型生成文本和工具调用，工具实时返回。 | 用户仍是静态任务，不会动态互动。 |
| Multi-turn user-interacting rollout | 模型、工具/数据库、LLM-simulated user 三方交互。 | 更复杂、更长、更随机，但更接近真实 agent。 |

MUA-RL 用第三种。训练时 user simulator 用 GPT-4o-2024-11-20，agent 温度设为 1.0 做探索，最多 30 个 interaction turns，最长 32768 tokens。

## RL 算法：GRPO

MUA-RL 使用 GRPO，也就是 Group Relative Policy Optimization。它不训练 value function，而是对同一个 query 采样一组 responses，用组内 reward 的相对高低计算 advantage。

论文的目标函数可以理解为：

```text
J_GRPO(theta) = E[ 1/G sum_i min( ratio_i * A_i,
                                  clip(ratio_i, 1-epsilon, 1+epsilon) * A_i )
                         - beta * D_KL(pi_theta || pi_ref) ]
```

其中：

```text
ratio_i = pi_theta(y_i | q) / pi_old(y_i | q)
```

解释：

- `pi_old`：采样 rollout 时的旧策略。
- `pi_theta`：正在更新的新策略。
- `pi_ref`：参考模型，用 KL 约束防止模型偏离太远。
- `A_i`：第 `i` 个 response 的 advantage。
- `clip`：限制更新幅度，避免策略一步变化太大。
- `beta * D_KL`：KL penalty，约束新模型不要过度偏离 reference。

advantage 用组内 reward 标准化：

```text
A_i = (r_i - mean({r_i})) / std({r_i})
```

也就是说，同一个任务下采样多个 rollout，做得比组内平均更好的 rollout 得正 advantage，做得更差的得负 advantage。这适合 tool-use 任务，因为最终 reward 通常是稀疏的 0/1。

## Reward：只看最终任务完成

MUA-RL 的 reward 很简单：

```text
r = 1  if task successfully completed according to system prompt
r = 0  otherwise
```

它刻意不加复杂的 format reward、tool-name reward、parameter matching reward 或成功调用工具次数 reward。

论文的理由是：动态用户交互里，过细的中间 reward 可能让模型学会钻格式或工具调用语法，而不是完成真实任务。只看最终完成有两个好处：

- 不惩罚不同的合理对话路径，只要最后任务完成即可。
- 降低 reward hacking：模型不能靠格式对、工具名对拿分，必须真的完成任务。

但这里也有风险：0/1 最终 reward 很稀疏，需要强 user simulator、可靠 verifier 和足够 rollout 才能学稳。

## Loss mask 策略

训练 loss 会 mask 掉 user messages 和 tool execution results，只让模型学习 agent 自己生成的 token。

这点很重要：

```text
用户说的话、工具返回的数据库结果：不是模型要模仿的行为
agent 的消息、tool call：才是模型 policy 要优化的行为
```

这和 Agent Lightning / Polar / AgentJet 里的 loss mask 思路一致。

## 实验设计

### 训练设置

- Backbone：Qwen3-8B / 14B / 32B Non-thinking。
- Cold-start：约 2000 条轨迹，覆盖 9 个场景，其中 5 个 synthetic scenarios，4 个真实 MCP server scenarios。
- RL 数据：TAU1-Bench 的 115 retail + 50 airline datasets。
- RL 框架：VeRL + GRPO。
- GRPO 参数：batch size 32，rollout number 8，25 epochs，KL coefficient `beta = 0.001`。
- User simulator：GPT-4o-2024-11-20。
- 评测：temperature 0.0，non-thinking mode，Function Calling mode。

### 评测 benchmark

| Benchmark | 测什么 |
|---|---|
| TAU1-Bench | 多轮 user-agent tool-use，retail / airline。 |
| TAU2-Bench | 比 TAU1 更严格，新增 telecom dual-control。 |
| BFCL-V3 Multi Turn | 多轮 function calling，包括 missing parameter / missing function / long context。 |
| ACEBench Agent | 多 step 和多 turn agent 工具任务。 |

TAU2 Telecom 还引入 TCR，也就是 Task Completion Rate。它不是只看成功/失败，而是看验证条件完成比例：

```text
TCR(q) = |{c_i in C_q : satisfied(c_i)}| / |C_q|
```

如果一个任务有 10 个检查点，agent 满足 6 个，TCR 就是 60%。它适合复杂任务，因为即使最终没全成功，也能看模型是否部分完成。

## 关键结果

### 1. TAU1 / TAU2

![TAU-Bench results](raw/2025-08_MUA_RL_2508.18669/assets/table1_tau_bench_results.png)

主要结果：

- MUA-RL-32B：TAU1 Retail `72.6`，TAU1 Airline `46.5`。
- MUA-RL-32B：TAU2 Retail `67.3`，TAU2 Airline `45.4`，TAU2 Telecom `28.3`。
- MUA-RL-14B：TAU2 Telecom `33.4`，TCR `54.3%`，超过 GPT-4o-2024-11-20 和 DeepSeek-V3-0324 在该表中的 telecom accuracy。
- Cold-start 在 retail/airline 上有帮助，但在 telecom 上可能退化；MUA-RL 能把这种 SFT bias 拉回来。

解读：MUA-RL 的收益不只是“工具格式更准”，而是让模型在用户互动和工具执行之间形成更稳的任务策略。Telecom dual-control 更复杂，因为用户也能操作共享状态，MUA-RL-14B 在这里的 TCR 提升尤其说明它能处理部分完成和复杂状态变化。

### 2. BFCL-V3 Multi Turn / ACEBench Agent

![BFCL and ACEBench results](raw/2025-08_MUA_RL_2508.18669/assets/table2_bfcl_acebench_results.png)

主要结果：

- MUA-RL-32B 在 BFCL-V3 Multi Turn overall accuracy 达到 `28.4`，高于 base `19.6` 和 cold-start `26.0`。
- MUA-RL-32B 在 ACEBench Agent overall accuracy 达到 `82.5`，仅低于 GPT-4.1 的 `86.7`，高于 DeepSeek-V3-0324 的 `74.2`。
- MUA-RL-14B 在 ACEBench Agent overall accuracy 从 base `60.0` 到 cold-start `70.0`，再到 MUA-RL `78.3`。

解读：BFCL 和 ACEBench 不是训练环境本身，能提升说明这个 recipe 有跨 benchmark 泛化，而不是只记住 TAU1 的工具和 policy。

### 3. 训练动态

![Learning curves](raw/2025-08_MUA_RL_2508.18669/assets/fig5_learning_curves.png)

论文分析了 KL loss、entropy、grad norm、rollout turns、response length、Unique 4-gram ratio、All Correct Query Ratio、All Wrong Query Ratio。

关键读法：

- KL loss 上升：模型逐渐偏离 cold-start/reference，说明 RL 确实在改变行为。
- 8B 波动更大：小模型容量有限，在探索和 KL 约束之间更不稳定。
- entropy 下降：模型从广泛探索转向更确定的策略。
- grad norm 稳定：没有明显梯度爆炸或发散。
- rollout turns 稳定在约 `21-23`：性能提升不是靠无限拉长输出，而是靠更结构化的多轮互动。
- response length 基本不变：不是 test-time scaling 式“写更长就更好”。
- All Correct Query Ratio 上升、All Wrong Query Ratio 下降：模型从偶尔成功变成更稳定成功，灾难性失败减少。

### 4. 工具调用趋势

![Tool invocation trends](raw/2025-08_MUA_RL_2508.18669/assets/fig6_tool_invocation_trends.png)

Calculate、Think、Transfer to Human Agent 三个通用工具的调用次数整体下降。

这不是说工具不重要，而是说明模型学会减少对低贡献工具的依赖。例如 non-thinking 模型一开始可能频繁调用 Think 工具，RL 后能更直接完成任务，决策路径更短。

### 5. Ablation：cold-start 和 RL 都必要

![Ablation study](raw/2025-08_MUA_RL_2508.18669/assets/table3_ablation.png)

对 MUA-RL-32B 做消融：

- `w/o RL`：只有 cold-start，没有 RL。
- `w/o cold-start`：直接从 base 做 RL。
- full MUA-RL：cold-start + RL。

结论：两个阶段都不能少。只做 cold-start 在某些 benchmark 有提升，但在 TAU2 Telecom 会退化；直接 RL 在 TAU2 上可能比 cold-start 更好，但 BFCL-V3 更差。完整 pipeline 在 TAU2 和 BFCL 上整体最好。

## 和前面论文的区别

### 和 Agent Lightning

Agent Lightning 解决“已有 agent execution 怎么抽成 transition”。MUA-RL 解决“rollout 里用户也应该是动态参与者”。

可以组合：Agent Lightning 负责 trace/transition 接口，MUA-RL 负责把 user simulator 和真实工具环境放进 rollout。

### 和 AgentJet

AgentJet 是训练基础设施，关注 swarm server/client、timeline merging、多模型训练。MUA-RL 是训练任务 recipe，关注 simulated user、最终任务 reward 和多轮用户交互。

可以组合：用 AgentJet 的 client 跑 MUA-RL 的 user simulator + tool environment，用 server 做 GRPO。

### 和 tau-bench / tau2-Bench

tau-bench 和 tau2-Bench 是评测环境；MUA-RL 把类似的 user-agent-tool 交互变成训练 loop。尤其 TAU2 Telecom 的 dual-control 和 MUA-RL 的目标很贴近，因为它要求模型处理用户和 agent 共同改变状态的情形。

## STAR 分析

| 项 | 内容 |
|---|---|
| Situation | 真实 agent 不是面对固定 prompt，而是在用户不断补充、修改和确认需求的过程中调用工具完成任务。 |
| Task | 训练模型在多轮用户交互中同时学会沟通、澄清、遵守 policy 和正确调用工具。 |
| Action | 先用合成/真实 MCP 工具轨迹做 cold-start，再把 LLM-simulated user、真实工具/数据库和最终任务 reward 放进 GRPO rollout。 |
| Result | 在 TAU1/TAU2、BFCL-V3 Multi Turn、ACEBench Agent 上整体超过 base 和 cold-start，32B 在多个任务上接近或超过更大模型，训练动态显示成功率更稳定、灾难性失败下降。 |

## 和我的研究方向的关系

### 对 agent harness

MUA-RL 提醒我们：harness 里不应只有 environment/tool simulator，还应该有 user simulator。一个面向真实交互的训练 harness 至少要记录：

```text
user message -> agent message/tool call -> tool/database observation -> user follow-up -> final state reward
```

如果用户模拟器足够强，它可以让 agent 在训练阶段学会追问、确认、拒绝、解释和执行，而不是上线后才在真实用户身上试错。

### 对 interaction model / HCI

这篇很接近 interaction model，但仍偏工程训练。它没有研究真实人类用户如何感受 agent，也没有处理用户信任、控制权、打断、可解释性。但它提供了一个很有用的训练视角：**用户行为是环境的一部分**。

对于 HCI/人机协作，我们可以继续问：

- user simulator 是否真的像人？
- agent 学到的是服务策略，还是适配 GPT-4o user simulator 的策略？
- 如何加入真实人类反馈、纠错和偏好？

### 对机器人 / embodied agent

如果迁移到机器人，user simulator 可以模拟人类指令、纠正和中途改目标；tool/database observation 可以替换成机器人传感器和环境状态。但 MUA-RL 当前没有视觉、动作控制和安全约束，不能直接当 embodied RL 方法。

### 对 memory

多轮 user-agent 交互天然需要短期任务记忆：用户身份、订单、已确认细节、已调用工具、policy 约束。MUA-RL 没有提出长期 memory 模块，但它的轨迹可以用于训练 agent 维护任务状态和避免重复问用户。

## 局限和不要误读

- 不要把 simulated user 等同真实用户。训练用 GPT-4o user simulator，模型可能学到 simulator 的行为偏差。
- reward 过于稀疏。最终 0/1 reward 简洁，但依赖可靠 evaluator，也可能学习慢。
- 没有细粒度 reward 不代表没有 reward hacking，只是减少格式型 hacking；模型仍可能找到任务判分漏洞。
- 训练主要在 TAU1 retail/airline 上做，跨到 TAU2/BFCL/ACEBench 是泛化评估，但 domain 仍集中在工具/客服类任务。
- 成本不低：多轮 rollout + GPT-4o user simulator + 真实数据库环境，比静态 benchmark 训练贵得多。
- 论文没有讨论真实用户安全、隐私、情绪、满意度或交互负担。
- appendix case study 说明模型更谨慎地确认用户意图，但这仍是个例，不等于完整行为安全证明。

## 可复用点

1. 在 agentic RL 训练 loop 里加入 user simulator，而不是只用静态 prompt。
2. reward 尽量对齐最终任务状态，而不是奖励中间格式。
3. loss mask 掉 user/tool tokens，只优化 agent-generated tokens。
4. cold-start + RL 两阶段比直接 RL 更稳。
5. 用 TCR 这类 partial completion metric 分析复杂任务，不只看 0/1 成功率。
6. 在训练动态里同时看 KL、entropy、grad norm、turns、response length、all-correct/all-wrong ratio。
7. 用 case study 检查 agent 是否学会确认、遵守 policy 和避免过早执行副作用操作。

## 下一步问题

- user simulator 的质量如何评估？它和真实用户分布差多少？
- 能否把 MUA-RL 接到 AgentJet/Polar 的 endpoint capture 和 timeline merging 上，降低多轮 rollout 成本？
- 最终 0/1 reward 是否足够训练更开放的 HCI/机器人任务？什么时候需要中间 reward？
- dual-control 场景下，如何区分 user action 和 agent action 的责任？
- 如果用户 simulator 诱导 agent 违规，训练会不会放大不安全行为？
- 对长期陪伴/机器人协作，如何加入真实人类偏好、打断、情绪和安全反馈？

## 记忆钩子

`MUA-RL = cold-start tool-use SFT + LLM-simulated user in RL rollout + real-time tool/database execution + final task reward + GRPO`。

这篇最值得记住的是：**在用户交互型 agent 里，用户不是静态 prompt，而是 RL 环境的一部分。**
