# AgentJet

## 一句话结论

AgentJet 是一篇 **agentic RL 训练基础设施论文**。它不是提出一个新的 reward，也不是一个新的 RL 算法，而是把 agent 执行和 GPU 训练拆成分布式 swarm：**swarm server 负责模型、优化器、推理 endpoint 和 context tracking；swarm client 负责跑 agent、环境、工具、reward 和评估**。

这篇可以看成 Agent Lightning 之后的系统扩展：Agent Lightning 解决“已有 agent trace 怎么变成可训练 transition”，AgentJet 解决“这些 agent rollout、多个任务、多个模型、多个 runtime 怎么在真实集群上稳定训练”。

![AgentJet swarm architecture](raw/2026-06_AgentJet_2606.04484/assets/fig1_swarm_architecture.png)

## 这篇放在阅读路线里的位置

前面几篇的分工可以这样串起来：

| 论文 | 主要解决什么 |
|---|---|
| Agent Lightning | 已有 agent runtime 怎么抽成 transition 并接入 trainer。 |
| AgentRL | 多环境、多任务 rollout-training 怎么异步扩展。 |
| ARPO | 工具返回后的局部探索和 advantage attribution。 |
| CacheRL | rollout 太贵时怎么缓存、蒸馏和复用轨迹。 |
| Polar | 黑盒 coding harness 怎么用 model API proxy 捕获 token-faithful trajectories。 |
| AgentJet | 多模型、多 client、多任务、多 runtime 的 agentic RL 怎么在 swarm 上稳定跑。 |

所以 AgentJet 的价值主要在工程系统层。它关心的是：如果我们真的要做 agentic RL 实验，不只是跑一个 toy benchmark，而是要同时跑 AppWorld、AIME、Werewolf、多 agent 游戏、翻译 pipeline、自动化 ablation，那训练框架应该怎么组织。

## 它解决什么问题

传统 LLM RL 框架通常假设 rollout worker、inference engine 和 trainer 在同一个集群、同一个 runtime 里协调。这对单轮数学推理还可以，但对 agentic RL 很脆弱：

- agent rollout 依赖外部环境，比如 Docker、浏览器、数据库、API、MCP 服务、搜索服务。
- 一个外部服务失败可能让整个训练 pipeline 崩掉。
- 想改 agent 代码或 reward function，往往要重启模型加载、vLLM/SGLang、优化器，迭代慢。
- 多 agent 任务可能需要不同模型，比如 7B 执行、32B 规划、235B 静态对手。
- 多任务 cocktail training 里的任务 runtime 可能互相冲突，例如 AppWorld 需要 stateful app API，AIME 只需要轻量 verifier。
- 多轮 agent 的 context 会反复包含系统提示、工具定义、历史 observation，训练时大量重复 token 会浪费 actor update 时间。

AgentJet 的核心回答是：**把训练平面和执行平面彻底拆开**。

## 方法 / 系统怎么做

### 1. Swarm architecture：server 训练，client 跑 agent

AgentJet 有两类节点：

| 节点 | 做什么 | 是否需要 GPU |
|---|---|---|
| Swarm Server | 保存模型权重、优化器状态、vLLM/SGLang 推理 endpoint、context tracker、sample pool，并执行 policy gradient update。 | 需要 GPU |
| Swarm Client | 跑 agent loop、任务环境、数据集、工具、reward function、评估逻辑和实验控制。 | 通常 CPU 即可 |

训练网络是动态 swarm：client 可以加入、退出、重启、替换；server 可以有多个，每个 server 训练一个模型。这样就能支持：

- 多个 client 给同一个 server 贡献 rollout。
- 一个 client 同时调用多个 server，训练非共享参数的多 agent 系统。
- 不同 client 运行在不同 Docker、虚拟机、操作系统或物理机器上。
- client 崩掉只影响自己，不会杀掉 GPU trainer。

### 2. Swarm RL 流程：OpenAI-compatible endpoint 是边界

![Swarm RL paradigm](raw/2026-06_AgentJet_2606.04484/assets/fig2_swarm_rl_paradigm.png)

AgentJet 的一次训练大致是：

1. server 启动，先只注册地址，不一定立刻加载模型。
2. controller client 发送训练参数，唤醒 server，server 加载模型和优化器。
3. client 为一个 episode 向 server 注册，拿到 episode-specific 的 `BaseUrl/APIKey`。
4. agent 像调用 OpenAI API 一样调用这个 endpoint。
5. server 拦截每次 LLM 请求，记录上下文、token、logprob 和 loss mask。
6. episode 结束后 client 提交 reward、task id 和 metadata。
7. server 把轨迹放进 sample pool。
8. sample pool 达到触发条件后，server 做 timeline merging，再执行 RL update。

这和 Agent Lightning/Polar 很像，都把 model API boundary 当成采集点。区别是 AgentJet 进一步把这个采集点做成分布式训练网络。

### 3. Sample pool 和 C1-C5：什么时候触发一次 update

AgentJet 不强制用固定同步 batch。它把完成的 episode 按 task id 放进 pool：

```text
B = {(t_i, E_i)}
```

其中 `t_i` 是任务 id，`E_i = {e_i^1, ..., e_i^m}` 是这个任务已经完成的 episodes，每个 episode 有 reward `r_i^j`。

它提供五种触发策略：

| 策略 | 触发条件 | 适合什么 |
|---|---|---|
| C1 episode-count | 总 episode 数达到 `B x N`。 | 简单吞吐优先。 |
| C2 task-count | 至少 `B` 个任务各自收满 `N` 次重复 rollout。 | GRPO 这类需要同题多采样的训练。 |
| C3 non-dummy task-count | 只统计 reward 有方差的任务。 | 避免全 0 或全 1 reward 任务提供无效 advantage。 |
| C4 all-clients-agree | 所有 active clients 都同意更新。 | 需要控制每个 client 贡献比例的异构训练。 |
| C5 any-client-agrees | 任一 client 同意就更新。 | 快速实验或低延迟更新。 |

这里的重点是：agentic RL 里的 episode 完成时间差异很大，不能简单假设所有 rollout 同步返回。C1-C5 是为了在吞吐、稳定性、任务均衡之间做取舍。

### 4. Context tracker：一条 timeline 记录什么

AgentJet 拦截每次 LLM call 后，会为它记录一条 timeline。timeline 由多个 message block 组成：

```text
T_i = (B_i^[1], B_i^[2], ..., B_i^[K_i])
B_i^[k] = (m_i^[k], x_i^[k], a_i^[k], l_i^[k], mu_i^[k])
```

逐项解释：

- `m_i^[k]`：这段 message 的文本。
- `x_i^[k]`：这段 message 对应的 token ids。
- `a_i^[k]`：作者标签，例如 `llm`、`env`、`user`。
- `l_i^[k]`：每个 token 的 log probability。
- `mu_i^[k]`：loss mask，只有 LLM 生成的 token 通常是 1，用户/环境/tool 文本是 0。

这和 Polar 的 token-faithful trajectory 很接近。区别是 AgentJet 不只是捕获轨迹，还要在 server 端直接进入训练更新。

### 5. Timeline merging：为什么能加速

多轮 agent 会产生很多高度重复的 prompt。比如：

```text
T1 = user prompt + model output 1
T2 = user prompt + model output 1 + tool result + model output 2
T3 = user prompt + model output 1 + tool result + model output 2 + tool result + model output 3
```

如果把 `T1/T2/T3` 都当成独立训练样本，前面的 prompt 和历史回复会被重复算很多遍。AgentJet 的 timeline merging 做的是：如果短 timeline 是长 timeline 的前缀，就把短的吸收到长的里面，同时保留哪些 token 是 LLM 生成、需要训练的。

![Timeline merging algorithm](raw/2026-06_AgentJet_2606.04484/assets/alg1_timeline_merging.png)

形式上，长 timeline `S` 和短 timeline `T` 可合并，如果：

```text
|S| >= |T|
Match(S^[k], T^[k]) = True, for all k in [1, |T|]
```

`Match` 可以有两种：

- `token`：token id 完全一致，最严格，train-inference consistency 更好。
- `text`：文本一致即可，默认更激进，能合并更多，但可能牺牲 token 级一致性。

![Text-level vs token-level timeline matching](raw/2026-06_AgentJet_2606.04484/assets/fig5_timeline_matching.png)

图 5 的 Qwen3 例子说明了一个真实坑：chat template 可能在后续 turn 里去掉旧 assistant message 的 thinking block，导致文本看似一致，但 token 序列不一致。text-level matching 会合并，token-level matching 不会合并。

这就是 AgentJet 的一个核心 trade-off：**训练速度 vs. token-faithful 一致性**。

## 输入、输出、数据类型、模态

| 维度 | AgentJet 里的定义 |
|---|---|
| 输入 | 任务数据集、agent loop、工具/环境、reward function、一个或多个待训练 LLM、swarm server/client 配置。 |
| 中间数据 | episode id、OpenAI-compatible requests、timelines、token ids、logprobs、loss masks、sample pool、task id、reward。 |
| 输出 | 训练后的 LLM/LoRA 权重，以及可复盘的 episode timelines 和实验报告。 |
| 模态 | 主要是文本 agent + tool/API 环境；没有直接做视觉、音频、机器人连续控制。 |
| 模型吃什么 | 每次 agent 调用 server endpoint 时的真实 chat/completion context。 |
| 模型输出什么 | LLM response、工具调用文本、游戏发言、翻译文本、数学解题步骤等，取决于 client 的 agent loop。 |
| reward | 由 client 计算，可以是游戏胜负、答案正确率、LLM-as-judge 分数、AppWorld 成功率等。 |

## 关键实验和结果

### 1. Shared-parameter multi-agent：Werewolf

Werewolf 是多智能体社交推理游戏，属于 POMDP。POMDP 指 partial observable Markov decision process，也就是每个 agent 看不到完整状态，只能根据自己的局部观察做决策。这里很适合测 deception、role consistency、implicit coordination。

实验设置是 9 人局：3 个 werewolves、3 个 villagers、1 个 seer、1 个 witch、1 个 hunter。可训练 agent 使用 Qwen2 7B 或 14B，共享参数；静态对手用 Qwen3-235B-A22B。

![Shared-parameter werewolf results](raw/2026-06_AgentJet_2606.04484/assets/table1_shared_werewolf.png)

主要结果：

- Werewolf 7B：`23.0% -> 47.2%`。
- Werewolf 14B：`40.9% -> 64.7%`。
- Seer 单角色：`38.5% -> 46.5%`。
- 非 werewolf 全队：`23.9% -> 41.6%`。

怎么理解：werewolf 更容易训，因为 reward 与团队胜负更直接，且 deception 策略可以从语言行为中学出来。witch/hunter 这种一次性能力角色提升较小，因为可学习决策点更少。

### 2. Non-shared-parameter multi-agent：行为多样性

![Non-shared parameter werewolf results](raw/2026-06_AgentJet_2606.04484/assets/table2_nonshared_werewolf.png)

非共享参数实验让不同 agent 或角色组使用不同 14B-LoRA 模型。关键结果是：

- 共享 14B werewolf：final success rate `64.7%`。
- 三个 werewolf 分别用三个 14B-LoRA：final success rate `66.5%`。

提升只有 `+1.8%`，但含义重要：社交推理里行为多样性本身有价值。如果三个 werewolf 共享参数，可能说话和投票模式太像，容易被识别；非共享参数让每个 werewolf 形成不同 persona，更不容易暴露。

这就是 AgentJet 相比很多单模型 RL 框架的卖点：它可以让多个 trainable model 在同一个任务里同时训练，而不是强迫所有 agent 共享一个 policy。

### 3. Multi-task cocktail training：一个模型同时学 AppWorld 和 AIME

Cocktail training 指一个 server 上训练同一个 Qwen3-8B，同时接两个 client：

- AppWorld client：长程工具/API 任务。
- AIME client：数学推理任务。

每步 batch 是 16 条 AppWorld + 16 条 AIME，和两个单任务 baseline 各自 batch 32 对比。

![Cocktail training](raw/2026-06_AgentJet_2606.04484/assets/fig7_cocktail_training.png)

结果：

- AIME：cocktail 和 separate 基本接近，全程均值约 `0.72 vs 0.73`。
- AppWorld：cocktail 明显落后，约 `0.58 vs 0.68`。

解释：AIME 是短程符号推理，和混合训练比较兼容；AppWorld 是长程工具任务，梯度信号更容易被短任务稀释。所以 cocktail training 的价值不是每个任务都超过 specialist，而是用一次训练得到一个 multi-skill generalist，省掉多个 specialist 和后续 distillation。

### 4. Timeline merging：AppWorld 上 6.25x 加速

![Timeline merging speedup](raw/2026-06_AgentJet_2606.04484/assets/fig8_timeline_merging_speedup.png)

在 AppWorld 的前 25 个训练 step 上，对比是否启用 timeline merging：

- reward 曲线基本重合。
- 每步 LLM call 数接近：`11.4 +/- 0.7` vs. `12.6 +/- 1.0`。
- actor-update wall time 从 `2160 +/- 171s` 降到 `346 +/- 13s`。
- 平均 `6.25x` 加速。

这说明加速主要来自去掉重复 context，而不是改变 agent 行为或减少 rollout 数。

### 5. Framework-agnostic：OpenAI SDK / LangChain / AgentScope / Raw HTTP

论文还做了同一 Qwen3-8B GRPO recipe，在四种 agent loop 实现上训练：

- OpenAI Python SDK
- LangChain
- AgentScope
- Raw HTTP

最终 held-out eval reward spread 只有 `0.025`，任意对齐 checkpoint 的最大差距小于 `0.04`。这说明 AgentJet 确实是在 OpenAI-compatible endpoint 层捕获训练信号，而不是依赖某个 agent 框架内部 instrumentation。

### 6. Vibe training 和 A3R：自动化 agentic RL 研究

AgentJet 还提出两个研究辅助模块：

- AVT / vibe training：研究者用自然语言描述任务、环境、reward 和 GPU 配置，coding agent 生成 swarm client 和训练代码。
- A3R / AgentJet Alpha Auto Research：leader agent 规划多阶段实验，worker agents 在多个 GPU 服务器执行、监控、恢复和汇报。

![A3R pipeline](raw/2026-06_AgentJet_2606.04484/assets/fig12_a3r_pipeline.png)

A3R 的核心单位是 experiment blueprint，里面包含目的、代码路径、虚拟环境、配置文件、命令、结果目录、时间预算和备注。它把长达数天的 RL ablation 变成可审计、可复现、可并行派发的实验计划。

一个案例是自动寻找 AIME swarm-mode GRPO 的最小稳定 batch size。A3R 用约 3 天、19 个 PAI jobs 完成三阶段 sweep。结论是：

- `mr=10000` 时，高性能稳定 batch size 约为 `bs=16`。
- batch 增大到 32 或 64 不再提升。
- response length 更关键：`mr=12000, bs=16` 达到最强，`pass@1=60.00%`，`pass@2=73.33%`。
- 省算力推荐：`bs=4, mr=12000`。

这里的重点不是这些超参本身，而是 A3R 展示了自动化 RL 研究流程：先粗扫，再根据结果细化，再处理失败 job，再生成最终建议。

## 和我的研究方向的关系

### 对 agent harness

AgentJet 强烈提示：如果我们自己做 agent harness，应该把“执行层”和“训练层”分开设计。一个实用 harness 至少要有：

```text
agent client runtime
-> model endpoint boundary
-> context tracker
-> reward/eval submit
-> sample pool
-> trainer update
```

这样后面不管接 RL、SFT、failure replay 还是自动 eval，都不会被某个 agent framework 绑死。

### 对 interaction model / HCI

AgentJet 本身不是 HCI 论文，但它的 client/server 边界很适合人机协作 agent：

- 用户可在 client 侧中断、修改、重启 agent。
- reward function 可以接人类反馈或偏好判断。
- client 可以保留完整可审计 timeline，用于解释 agent 为什么这么做。
- hot-swap debugging 适合快速改 interaction policy。

但它没有直接处理用户体验、透明度、控制权和 consent，这些仍需要 HCI 论文补足。

### 对机器人 / embodied agent

AgentJet 对机器人方向的启发是 runtime isolation。真实机器人 rollout 昂贵、慢、容易出错，而且和 GPU trainer 往往不在同一台机器上。server/client 拆分很自然：

- server：训练 VLA/LLM policy。
- client：连接机器人、仿真器、传感器、控制栈、安全检查和人类监督。

但当前论文没有做视觉、连续控制、真实机器人，也没有处理 latency-sensitive control，所以不能直接当 robotics RL 框架。

### 对 memory / experience replay

timeline merging 和 context tracker 可以作为 experience memory 的底层数据格式。每次 LLM call 都有 token、logprob、mask、author、reward metadata，以后可以做失败检索、经验回放、反思总结或 verifier 训练。

## 局限和不要误读

- 不要把它当成新 RL 算法。它主要复用 GRPO/PPO 这类现有优化方法，贡献在训练系统。
- 不要把 A3R 当成可靠科学家。它能自动跑 ablation 和生成报告，但仍依赖人类定义研究问题、检查 reward hacking、判断结论是否有意义。
- Vibe training 暴露了 reward hacking 问题：Who is the Spy 里 agent 一开始靠复述别人发言拿高分，必须修 reward 才能纠正。
- 多任务 cocktail training 有性能税，尤其对 AppWorld 这种长程工具任务，specialist 仍然更强。
- timeline merging 的 text-level matching 会牺牲 token-level train-inference consistency，严格训练时要谨慎。
- 论文主要是文本/tool/API agent，没有覆盖多模态、实时交互和机器人连续控制。
- 许多结果展示的是 framework capability，不是证明某个任务上 SOTA。

## 可复用点

1. 用 OpenAI-compatible endpoint 作为 agent runtime 和 trainer 的边界。
2. server 保存 model/optimizer/context tracker/sample pool，client 保存 agent loop/environment/reward/eval。
3. 每个 episode 使用 episode-specific `BaseUrl/APIKey`，避免跨 episode 混淆。
4. 把 sample pool 按 task id 组织，支持同题多采样和 reward variance 过滤。
5. 对多轮 agent 做 timeline merging，减少重复 context 的训练成本。
6. 用非共享参数 multi-agent training 保留角色差异和行为多样性。
7. 对复杂任务采用 client 隔离，而不是把所有依赖塞进同一个 monolithic trainer。
8. 用 blueprint 记录自动化实验，保证长程 RL ablation 可审计、可复现。

## 下一步问题

- AgentJet 的 endpoint capture 能不能和 Agent Lightning 的 transition abstraction 合并成统一数据格式？
- timeline merging 在有 tool call side effect、memory compaction、retrieval cache 时是否仍然安全？
- C3 non-dummy sampling 会不会偏向 reward variance 高但不一定重要的任务？
- Cocktail training 的任务配比应该怎么自动调，而不是手工给每个 client batch？
- 对机器人/VLA，client 侧如何把视觉状态、连续动作和安全约束写成可训练 timeline？
- A3R 自动研究如何防止 reward hacking、错误结论和实验选择偏差？

## 记忆钩子

`AgentJet = swarm server/client + OpenAI-compatible endpoint + context tracker + timeline merging + multi-model/multi-task agentic RL infrastructure`。

它最值得记的不是某条 reward 曲线，而是这个系统判断：**agentic RL 的难点已经从“会不会写 PPO/GRPO”扩展到“能不能稳定组织真实 agent runtime、外部环境、多个模型、多任务 rollout 和长程实验”。**
