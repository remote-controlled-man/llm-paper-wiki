# SENTINEL

## 一句话结论

SENTINEL 的核心思想是：**不要一直拿固定的一批通用任务做 RL，而是让模型先在环境里失败，再把这些失败轨迹总结成 failure modes，生成专门针对这些弱点的新训练任务。**

它把 agentic RL 的数据生成从“预先写一堆任务”变成“根据当前模型不会什么，动态生成下一批任务”。这对 tool-use agent 很重要，因为模型能力会随训练变化，固定任务集很快会变成太简单、太难、重复，或者和当前弱点不匹配。

![Failure-driven intuition](raw/2026-06_SENTINEL_2606.12908/assets/fig1_failure_driven_intuition.png)

## 这篇放在阅读路线里的位置

前几篇的关系可以这样串起来：

- Agent Lightning：已有 agent runtime 怎么接入 RL。
- AgentRL：多任务多轮 RL 怎么规模化训练。
- ARPO：在多轮工具调用里，怎么把 rollout 预算集中到关键分支。
- CacheRL：怎么用 cached rollout 降低环境执行成本。
- SENTINEL：怎么根据当前模型失败，动态生成更有训练价值的任务。

SENTINEL 解决的是一个很现实的问题：**RL 的训练任务分布会过期。**刚开始有用的任务，训练几轮后可能已经学会；一些任务又太难，rollout 全失败，没有有效梯度。SENTINEL 用失败轨迹做课程生成，让任务分布追着模型弱点走。

## 解决什么问题

普通 agentic RL 往往这样做：先准备一批训练任务，然后让模型反复 rollout，用 reward 优化。问题是：

- 如果任务太简单，模型都能过，reward 没差异，学不到东西。
- 如果任务太难，全部失败，也是学不到东西。
- 如果任务重复，模型可能记住套路，不提升泛化。
- 如果任务和当前模型弱点不匹配，rollout 被浪费。
- 如果 reward 或环境有漏洞，模型可能学会 exploit，而不是学会真正完成任务。

SENTINEL 的问题意识是：**当前模型的失败本身就是最好的训练信号。**失败轨迹告诉我们模型到底还不会什么：

- 选错商品 variant。
- 选错 order / user / record。
- 忘记执行 state-changing action。
- 没有按 policy 先问确认。
- 工具调用顺序不对。
- 工具参数错。

这些比随机生成任务更有针对性。

## 方法总览：Controller-Proposer-Solver Loop

SENTINEL 有三个角色：

1. **Solver**：正在训练的 tool-use agent，也就是 policy model。
2. **Controller**：看 Solver 的失败轨迹，总结 recurring failure patterns。
3. **Proposer**：根据 Controller 的诊断，生成新的 executable targeted tasks。

![SENTINEL loop](raw/2026-06_SENTINEL_2606.12908/assets/fig2_sentinel_loop.png)

整体循环是：

```text
Solver rollout -> failed trajectories
Controller analyzes failures -> failure patterns / directives
Proposer generates targeted executable tasks
Solver trains with RL on targeted task buffer
updated Solver rollout -> new failures
```

这就是 failure-driven RL：不是让任务生成器自由发挥，而是让失败轨迹约束下一批任务应该考什么。

## 关键模块 1：Solver

Solver 是实际要优化的模型。论文使用 Qwen3-4B-Thinking-2507。

在每个任务里，Solver 和 Tau2-Bench Retail 环境交互：

- 看用户请求和历史对话。
- 调用工具/API。
- 接收工具结果或用户模拟器回复。
- 继续多轮决策。
- 最终完成任务或失败。

一个轨迹可以写成：

```text
tau = (x, s0, a1, o1, ..., aT, oT, sT)
```

解释：

- `x`：用户任务。
- `s0`：初始环境状态，例如用户、订单、商品数据库。
- `a_t`：agent 在第 t 步的动作，可以是自然语言回复，也可以是工具调用。
- `o_t`：环境反馈，比如工具返回或用户回复。
- `s_T`：最终环境状态。

目标是最大化任务成功 reward：

```text
max_theta E[R_task(tau, x, E)]
```

也就是让模型在环境 `E` 中完成用户任务 `x` 的概率更高。

## 关键模块 2：Controller

Controller 负责把失败变成诊断。

每隔固定数量的 rollout，Controller 收集一批轨迹：

```text
T_t = {tau_i}_{i=1..n}
```

然后按 reward 阈值分成失败和成功：

```text
F_t = {tau_i in T_t : R(tau_i) < rho}
S_t = T_t \ F_t
```

解释：

- `F_t`：低 reward 失败轨迹，用来找当前模型弱点。
- `S_t`：成功轨迹，用来避免重复生成已经学会的任务。
- `rho`：失败阈值，实验里用 0.5 收集低 reward 轨迹。

Controller 会去重，避免同一个任务同一个失败 trace 重复分析。然后用 LLM analyzer 看：原始任务、gold actions、Solver 实际 tool calls、reward/penalty breakdown、对话历史，输出 failure patterns：

```text
P_t = {p1, p2, ..., pK}
```

failure pattern 不是笼统说“失败了”，而是具体说失败类型，例如：

- wrong item selection。
- missing state-changing action。
- wrong tool use。
- policy violation。
- premature termination。
- user-identification failure。

Controller 还维护训练历史：

```text
H_t = {(P_j, a_j, r_j)}_{j<t}
```

这样它能判断某个错误是持续存在，还是已经被解决。如果某类错误反复出现，就提高优先级；如果 related tasks 已经稳定通过，就降低优先级。

## 关键模块 3：Proposer

Proposer 的任务是生成新的训练任务，但有两个硬要求：

1. **必须 executable**：任务必须能在工具环境里真实执行，有合法参考轨迹。
2. **必须 targeted**：任务要专门刺激 Controller 发现的弱点。

它不是直接让 LLM 编一个用户请求和答案，因为那样容易出现任务和工具轨迹不一致。SENTINEL 采用 trajectory-grounded task construction：

1. 先在环境中采样相关状态，例如用户、订单、商品、可用工具。
2. 生成并执行一条可行的 reference tool-use trajectory。
3. 再把这条轨迹改写成自然语言用户请求。
4. 用户请求隐藏解法路径，但保留目标和约束。

这样生成的任务是 self-consistent 的：因为任务来自一条已经可执行的轨迹。

如果 Controller 发现模型总是选错相似商品，Proposer 就生成包含相似商品名、不同尺寸/颜色/材质的任务。如果发现模型没按 policy 问确认，Proposer 就生成需要确认后才能执行 state-changing action 的任务。

## 关键模块 4：Reward 和 GRPO

SENTINEL 用 GRPO 训练 Solver。每个 prompt 采样 8 条 response/rollouts，并用动态过滤去掉全 0 或全 1 reward 的 prompt group，因为这些组没有有效相对优势。

Reward 包含：

- **Task-success reward**：最终数据库状态是否对，最终回复是否正确沟通。
- **Action-level authentication check**：state-changing tool call 前是否完成 policy 要求的身份验证/确认；缺失则 reward 减 0.5。
- **Tool-format penalty**：工具格式错误，-0.1。
- **Repeated-tool-call penalty**：连续重复相同工具调用，-0.15。
- **Length penalty**：每个 excess assistant token，-0.0001。

这几个 shaping 项目的目的不是“让 reward 更花哨”，而是防 reward hacking：防止模型用工具循环、超长推理、格式乱写等方式骗过或干扰最终判分。

## 实验设置

环境：Tau2-Bench Retail。

这是一个多轮客服工具调用 benchmark，任务包括：

- 取消订单。
- 商品换货。
- 退货处理。
- 查询用户、订单、产品记录。
- 遵守 domain policy，比如某些操作前必须身份验证或用户确认。

模型和训练：

- Base model：Qwen3-4B-Thinking-2507。
- User simulator：Qwen3-235B-A22B-Thinking-2507 via SGLang。
- RL framework：Slime。
- RL algorithm：GRPO + Trajectory Importance Sampling。
- rollout batch size：16。
- 每个 prompt 采样 8 responses。
- KL coefficient：0.001。
- clipping range：0.2，高阈值 0.28。
- 每 12 个 rollout batches 触发一次 error analysis。
- 每次最多生成 10 个 synthetic tasks。
- 所有实验在 8 个 AWS P5 instances 上做。

为避免泄漏，训练环境和测试环境使用分离数据库；tool schemas 和 policies 相同，但 users、orders、products、environment states 不同。

## 指标：Pass^k 怎么理解

Tau2-Bench 报告 `Pass^k`，意思是同一个任务重复运行 k 次，**k 次都成功**的概率。

直觉：

- `Pass^1` 看单次成功率。
- `Pass^2` / `Pass^3` 看稳定性。
- 如果模型偶尔成功但不可靠，`Pass^k` 会掉得很快。

这比只看一次 pass 更适合多轮 agent，因为真实部署里同类任务不能只靠运气成功一次。

## 主要结果

![Main results](raw/2026-06_SENTINEL_2606.12908/assets/table1_main_results.png)

Tau2-Bench Retail 上：

| Method | Pass^1 | Pass^2 | Pass^3 |
|---|---:|---:|---:|
| Base | 66.4 | 51.6 | 43.2 |
| General RL | 69.0 | 55.6 | 47.4 |
| SENTINEL | 74.9 | 60.5 | 51.2 |

关键解释：

- General RL 比 Base 有提升，说明额外 RL 任务确实有用。
- SENTINEL 比 General RL 更好，说明“针对当前失败生成任务”比“用广泛通用任务继续 RL”更有效。
- Pass^2 和 Pass^3 也提升，说明它不是只提高单次撞好运，而是提高重复成功稳定性。

## SFT 后再训练的结果

论文还问了一个更重要的问题：如果模型已经先 SFT 到比较强，failure-driven RL 还有效吗？

![SFT success rate](raw/2026-06_SENTINEL_2606.12908/assets/fig3_sft_success_rate.png)

结果：

- Base：66.4。
- SFT：74.3。
- SFT + General RL：68.1，反而下降。
- SFT + SENTINEL：78.1，继续提升。

这张图很重要。它说明：当模型已经比较强时，继续用广泛通用任务做 RL 可能破坏原来学到的行为，甚至学到退化策略，比如工具循环或 reward exploit。SENTINEL 因为只针对 remaining weaknesses 生成任务，所以更像“补短板”，不容易把已经学会的行为冲坏。

## Failure Pattern 分析

![Failure patterns](raw/2026-06_SENTINEL_2606.12908/assets/table2_failure_patterns.png)

Controller 发现的 failure modes 不是简单的“不会调工具”，而是更细：

| Failure type | 典型错误 | 生成任务策略 |
|---|---|---|
| Missing required action | 需要计算差价，但模型没有用 calculate tool | 生成必须沟通差价的任务。 |
| Item/argument selection | 意图对了，但选错 product variant 或 item id | 生成含相似商品、相似 record 的任务。 |
| Multi-record reasoning | 多个订单/商品混淆，把操作作用到错误订单 | 生成多订单、重叠商品、不同约束的任务。 |
| Execution control | policy 要求用户确认，但模型直接执行 | 生成必须澄清/确认才能继续的任务。 |

这说明随着 base/SFT 模型变强，剩下的错误更像“精细执行错误”：不是不知道工具存在，而是在正确时间、正确记录、正确 policy 条件下调用正确工具。

## STAR 分析

| 项 | 内容 |
|---|---|
| Situation | 固定任务集做 agentic RL 会很快和当前模型能力错配：太简单、太难、重复，或不针对当前错误。 |
| Task | 让训练任务随模型失败动态变化，把失败轨迹变成针对性训练任务。 |
| Action | 设计 Controller-Proposer-Solver loop：Controller 诊断失败，Proposer 生成 executable targeted tasks，Solver 用 GRPO 在任务 buffer 上训练。 |
| Result | 在 Tau2-Bench Retail 上，Pass^1 从 66.4 提升到 74.9；在 SFT 后，General RL 降到 68.1，而 SENTINEL 提到 78.1。 |

## 和前面论文的关系

### 和 CacheRL

CacheRL 解决 rollout 成本，SENTINEL 解决 rollout 任务分布。

可以组合成：

```text
CacheRL: 让 rollout 更便宜
SENTINEL: 让 rollout 更有针对性
```

但组合时要小心：SENTINEL 依赖失败轨迹真实反映模型弱点。如果 CacheRL 的缓存结果不准，Controller 可能把 cache mismatch 误诊成模型失败。

### 和 Agent Lightning

Agent Lightning 可以提供统一 trace/transition 接口。SENTINEL 可以消费这些 trace，把低 reward 轨迹交给 Controller 做 failure analysis。

组合方式：

```text
Agent runtime trace -> transition/failure log -> Controller diagnosis -> targeted task generation -> RL update
```

### 和 AgentRL

AgentRL 是大规模多任务训练系统，SENTINEL 更像 curriculum / data generation layer。AgentRL 可以负责 rollout-training infrastructure，SENTINEL 负责决定下一批任务该长什么样。

### 和 ARPO

ARPO 在一个任务内部找高不确定分支，SENTINEL 在任务分布层面找当前模型的弱点。两者层级不同：

- ARPO：step/branch-level exploration。
- SENTINEL：task-level curriculum generation。

## 和我的研究方向的关系

### 对 agent harness

SENTINEL 对 harness 的要求很明确：日志必须足够结构化，才能诊断失败。

至少要记录：

- 用户任务。
- 环境初始状态。
- 每一步工具调用和参数。
- 工具返回。
- 最终环境状态。
- reward breakdown。
- gold/reference action 或 expected constraints。
- 失败原因分类。

如果只保存聊天 transcript，Controller 很难判断是 wrong item、missing action，还是 policy violation。

### 对可验证 reward

SENTINEL 很依赖 executable evaluator：

- DBCheck：最终数据库状态是否正确。
- CommCheck：是否把必要信息告诉用户。
- action-level check：中间操作是否符合 policy。

所以它和 tau-bench/tau2/Agent-Diff 这类 state-diff/verifier benchmark 非常搭。如果没有可验证环境，failure-driven task generation 可能会变成 LLM judge 自说自话。

### 对机器人 / embodied agent

这篇不能直接迁移到连续控制机器人，但思想有用：

- 机器人也可以从失败轨迹里总结 failure modes，例如 grasp pose 错、目标物 grounding 错、未确认人类意图、动作顺序错。
- Proposer 可以生成针对这些失败的仿真任务或数据采集任务。
- 但机器人需要更强的环境 grounding，不能只用 LLM 改写任务。

## 局限和不要误读

- 实验只在 Tau2-Bench Retail，一个受控客服工具环境；还没有证明可泛化到所有工具域。
- Controller 依赖 LLM analyzer，诊断质量可能影响后续任务质量。
- 任务生成只覆盖当前 Solver 暴露出来的失败；如果某些罕见失败没有被 rollout 采到，就不会被针对性训练。
- Proposer 生成任务虽然 trajectory-grounded，但仍可能有分布偏移或任务模板化。
- 训练成本不低：实验用了 8 个 AWS P5 instances。
- 没有深入比较不同 Controller/Proposer 模型、prompt、失败分类 taxonomy 的敏感性。
- 不解决 reward 本身错误的问题；如果 evaluator 错，failure-driven loop 会围绕错误信号优化。

## 可复用点

1. 把 failed rollouts 当作训练数据生成的输入，而不是只当评测错误。
2. 失败分析要同时看 failed 和 successful rollouts，避免重复练已经会的能力。
3. task generation 应该 trajectory-grounded：先有可执行参考轨迹，再改写用户任务。
4. failure mode 要具体到可训练维度：wrong argument、missing action、policy violation、multi-record confusion。
5. RL task buffer 应混合原始任务和 failure-targeted tasks，避免训练分布过窄。
6. 用 dynamic filtering 去掉全 0 / 全 1 reward 组，让 GRPO 保持有效相对优势。
7. 对 strong SFT model，general RL 可能伤模型；targeted RL 更像补短板。

## 下一步问题

- SENTINEL 的 Controller 能不能直接接 Agent-Diff 的 state-diff failure report？
- 如果把 CacheRL 的 cached rollout 接进来，怎么避免缓存错误被误诊成模型 failure？
- Controller 的 failure taxonomy 是否可以固定成可复用 schema，而不是全靠 prompt？
- 对 robot/human-agent interaction，失败轨迹能否生成 targeted simulation tasks 或 human correction tasks？
- failure-driven task generation 会不会过度聚焦当前弱点，牺牲 broader generalization？

## 记忆钩子

`SENTINEL = failed rollouts -> Controller diagnosis -> Proposer targeted executable tasks -> Solver GRPO`。

这篇最重要的启发是：**agentic RL 不只是优化算法问题，也是训练任务分布管理问题。**固定任务集会过期；失败轨迹能告诉你下一批任务该练什么。
